# INT Node.js Engineering Standards
You are assisting an engineering team at INT. Whenever you write, refactor, or suggest Node.js code, you must strictly adhere to the following rules:

## 1. Code Style and Structure
* Use ES6+ syntax consistently. Prefer `const` and `let` over `var`.
* Always use `async/await` for asynchronous operations. Do not use raw Promises (`.then().catch()`) or callbacks unless interacting with a legacy library that strictly requires it.
* Keep functions small and modular. A single function should do one thing well.
* Use descriptive variable and function names. Avoid single-letter variables except in standard loops (like `i`, `j`).

## 2. Error Handling
* Wrap all asynchronous operations in `try/catch` blocks.
* Never swallow errors. Always log the error details using the project's standard logger (e.g., Winston or Pino), not just `console.log`.
* Return standard HTTP status codes and structured JSON error responses for API endpoints.

## 3. Security
* Never hardcode sensitive information like API keys, database credentials, or secrets. Always read these from environment variables (`process.env`).
* Validate and sanitize all incoming user payload data before processing it.
* Avoid using standard `eval()` or executing arbitrary code.

## 4. Performance
* Prevent event loop blocking. Offload heavy synchronous computations to worker threads or external services.
* Ensure database queries are optimized and use indexing where appropriate.

## 5. Guardrails
* Never include comments indicating that code was generated by AI.
* Never write default commit messages that gives hint of AI-Generated
* Do not add any AI-specific configuration files (like .cursorrules or .copilotignore) outside of the .agent/ directory.

## 6. PR Gate Governance
* Strictly enforce non-blocking parallel spec execution: Specs exist and progress independently.
* Enforce reviewer detection upon `git pull`: Authenticated Git user must match assigned reviewer to approve/reject PR gates.
* Enforce role separation: Pulling code does not grant approval rights.
* Maintain Dashboard HTML as single source of truth for full PR review records, synchronized simultaneously with `.spec.md`, dedicated `.ai-context/pr_reviews/` record files, `.ai-context/status.md`, and `.ai-context/prompt_history.md`.
* Scope restriction: Do not modify workflows before Spec Generation or after Gate 2 Approval.
* Pre-Development PR Review Check: Before starting development on any spec, inspect available PR Review records (`.ai-context/pr_reviews/GATE1-<slug>-*.md`) and notify the developer of review findings and feedback.
* Strict Gate 1 Rejection Block: If a spec was `Rejected` or marked `Changes Requested` at Gate 1, strictly block all planning (`.plan.md`), task generation (`.tasks.md`), test case drafting (`.test_cases.md`), and code implementation (`src/`). The user MUST update the spec (`.ai-context/specs/<slug>.spec.md`) and re-submit for Gate 1 approval.
* Approved Spec Development Lifecycle: Approved specs proceed through Plan (`.plan.md`) -> Tasks (`.tasks.md`) -> Test Cases (`.test_cases.md`) -> TDD RED (`tests/`) -> TDD GREEN (`src/`) -> Test Verification -> Gate 2 Review (`.ai-context/pr_reviews/GATE2-<slug>-*.md`).
* Change Request Keyword Rule: Trigger formal Change Request workflow (Spec revision & Gate 1 re-approval) ONLY when prompt explicitly contains "Change Request" or "CR". Prompts without "Change Request" are processed as Development-Related Fixes / UI Bug Fixes under the active approved spec.
